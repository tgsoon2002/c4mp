Written for: AI agents that read or edit c4mp .c4 plan files.

# c4mp `.c4` plan files: how they are organised and how to write them

Everything below was checked against the c4mp source and by running the commands on two scratch
repos (a small three-container sample and an empty "greenfield" repo). Where something could not be
verified it is marked UNVERIFIED.

## 1. What a .c4 plan is and where the files live

A plan is a set of plain-text `.c4` files describing the architecture you intend: a system, its
containers, their components, relations, links to code, and a status per part. c4mp scans the code,
reads the plan, and compares them (`c4mp check`, `c4mp view`).

Folders, in the order c4mp looks for plan files (first folder that contains at least one `.c4`
file wins; folders are never merged):

| Order | Folder | Notes |
|---|---|---|
| 1 | `config.architectureDir` (repo-relative) | Only if set in `.c4mp/config.json` or `C4MP_ARCHITECTURE_DIR`. |
| 2 | `<anchor>/.c4mp/projects/<projectId>/plan/` | The normal home. Anchor = nearest folder at or above `--repo` holding `.git` or `.c4mp`. |
| 3 | `<repo>/c4/` | Legacy, still read. |
| 4 | any `.c4` file anywhere under the repo | Fallback when none of the above has a `.c4` file. |

Also: `plan generate --out <dir>` writes to `<dir>` instead (the explicit flag wins for writing).
All `.c4` files in the winning folder (recursively) form ONE plan; file names do not matter.

`<projectId>` is the `package.json` `name` of the scan target, else the folder name, lower-cased
with dashes. Caution: `c4mp init` derives it from the FOLDER name only, the other commands use the
`package.json` name. In the sample repo (`package.json` name `sample-shop`, folder `c4guide`)
`init` created `.c4mp/projects/c4guide/` (left empty) and `plan generate` wrote to
`.c4mp/projects/sample-shop/plan/`. Use the folder that `plan generate` prints, or the one that
already holds `.c4` files.

c4mp writes automatically only inside `.c4mp/` and `C4MP/` (the map page). It never edits source code.

## 2. The model: system, container, component

```
system        one per scan target (the whole product)
  container   a deployable or top-level folder/service (an app, a worker, a database)
    subregion (optional) a named group of components inside one container, listed top to bottom
      component a group of code with one purpose
```

`subregion` -> a container; `component` -> a container or a subregion. A subregion holds components only to group
them; it has no link and claims no code. A component in a subregion has the fqn `system.container.subregion.component`.
Until plan standard 1.9 the kind was called `layer`: c4mp still reads `= layer` as `subregion`, writes `subregion`, and
`c4mp plan upgrade --repo . --yes` rewrites the old word in your plan files (dry run without `--yes`).

A subregion that every other subregion may use directly (types, small helpers) is a shared subregion: give it
`metadata { shared 'true' }`. The map draws it as a column on the right of the container, as tall as the stack of the
other subregions, which stay top to bottom on the left. One per container (a second one is drawn as a plain
subregion). Only a subregion may carry `shared`, and only with `'true'`; anything else is an `invalid-metadata` warning.

**Foundation components.** A component that nearly every other component uses (shared types, small helpers) can be
marked `metadata { role 'foundation' }` (`c4mp plan set <component> role=foundation`; remove it with
`--unset role`). The map draws it as tinted glass in its own colour with a "used by N" badge and hides the arrows
into it until you point at the box, zoom into it or select it; the arrows out of it stay. `c4mp check` suggests the
marker (`foundation-candidate`, info) for a component used by more than half of the other components; it never
sets it. Only a component may carry `role`, and only `'foundation'`; anything else is an `invalid-metadata` warning.

**Planning with layers (a suggestion).** Subregions used as layers pay off most as a direction rule, not only as
groups. A stack that fits many programs, top to bottom (each line one subregion):

```
Entry points      what people and tools call: CLI commands, API routes, UI, MCP tools, scripts
Services          one function per job: open the project, run a scan, edit the plan
Engines           the work itself: build, compare, check, lay out
Readers           read files, config, git, the database
Shared (column)   types and small helpers every layer may use (shared 'true')
```

- A component calls its own layer or a layer below, never up. An entry point calls Services, not Engines or Readers;
  Services call Engines and Readers. The shared layer may be used from anywhere.
- Plan a feature's path layer by layer before the code exists: which entry point, which service, which engine or
  reader. `c4mp plan path <entry> <target>` prints that route from the plan and the code: the layers between, the
  components there that already call the target, and a ready-made `plan add planned-fn` command where one is
  missing. If no service offers the job yet, plan the service function (`c4mp plan add planned-fn <name> --parent
  <service>`) instead of letting the entry point call the reader because the function already exists there.
- Why it pays: the setup a job needs is written once, in its service, not again in every command (C4MP's own command
  line opened a project with the same five or six reader calls in a dozen commands; one service function replaced
  them). A call is easy to trace: `c4mp deps <component>` shows a few arrows, one layer down. The job's tests sit on
  the service instead of being repeated for each entry point.
- `c4mp check` reads the direction from the subregion order (declaration order, first = top): `layer-upward` (warning)
  for a code arrow into a layer above, in the same container; `layer-skip` (warning, off by default, config
  `"layers": {"skip": true}`) for an entry point that skips the services: an arrow from the top layer that jumps over
  the second one (a lower layer jumping over a layer is not reported), naming a component in between that already calls
  the target. A shared subregion is never the target of either rule. Read the arrows with `c4mp deps <fqn>`: an entry
  point with an arrow into a reader or an engine is a call that skips the services. `c4mp deps <fqn> --files` shows
  the import lines behind each arrow, so you know which lines to move; `c4mp deps <fqn> --compare <ref>` shows the
  arrows at a stored snapshot and now (new, gone, changed), with the old files mapped onto today's plan boxes.

The architecture map draws these four kinds and two actor kinds: `person` (a user) and `external` (an outside
system). An actor is a plan-only box drawn at C1, beside the system (the top level of the map becomes the "system
context": our system with its persons and externals around it); it needs no code link, and relations to and from it
are kept. A person drawn with a robot's square head instead of the round one (an AI agent) has `metadata { shape 'robot' }`
(`c4mp plan set <person> shape=robot`); `shape` is optional, `person` (the default) or `robot`. An `external` may hold containers (`cloud.web = container ...` under `cloud = external ...`): they are drawn
inside the external, never merged with a scanned container of ours (section 10, Q5). The parser accepts ANY word after `=` as a kind and `plan show` lists it, but an unknown
kind is drawn nowhere. The storage kinds below are known kinds, but the architecture map does not draw them (they are for the Storage view).

**Storage kinds** (the Storage view). Three more kinds describe stored data: `store`, `record`, `field`.
They need no code link (like `person` and `screen`).

```
container     an app, a service
  store       a place that keeps data (a database, a file, a folder, a bucket)
    record    a table, collection, row or file in the store
      field   a column or key; a field can hold fields (nested data)
```

A `record` sits only under a `store`. A `field` sits under a `record` or a `field`. The element's
`technology` line says which kind of store it is. c4mp picks the word to show from it:

| technology | store | record | field |
|---|---|---|---|
| postgres, mysql, sqlite | database | table | column |
| mongodb | database | collection | field |
| json, yaml | file | record | key |
| csv | file | row | column |
| fs | folder | file | field |
| s3 | bucket | object | field |
| redis | instance | key pattern | field |

Any other technology shows `store`, `record`, `field`.

Metadata keys for storage (all values quoted; not checked in plan standard 1.1, kept as written):

| On | Key | Value |
|---|---|---|
| field | `type`, `default` | any text |
| field | `pk`, `unique` | `true` |
| field | `nullable` | `true` or `false` |
| field | `values` | comma list: `new,paid,shipped` |
| field | `fk` | `<record>.<field>`, for example `customers.id` |
| field | `onDelete` | for example `cascade` |
| store | `reader` | a reader id, for example `drizzle`; wins over the technology |
| store | `source` | repo-relative file or folder with the store's code, no leading `./`, for example `src/db/schema` |
| record | `pk` | composite key: `col1,col2` |
| record | `index.<name>` | `[unique ]col1,col2[ where <expr>]` |
| record | `check.<name>` | an SQL expression |

Add them with `plan add --meta key=value` (repeat the option for more keys). Without `--yes`, `plan add` is a dry run and writes nothing:

```
c4mp plan add store Main --id main --parent shop.api --tech postgres --repo . --yes
c4mp plan add record customers --parent shop.api.main --repo . --yes
c4mp plan add record orders --parent shop.api.main --repo . --yes --meta "index.by_customer=customer_id,created_at"
c4mp plan add field id --parent shop.api.main.orders --repo . --yes --meta type=uuid --meta pk=true
c4mp plan add field customer_id --parent shop.api.main.orders --repo . --yes \
  --meta type=uuid --meta fk=customers.id --meta onDelete=cascade
```

To tie a store to its code, add `reader` and `source`. `plan show <store>` reads the code behind a store through its reader.
A named file is always read; a folder, or no `source`, is searched by the reader.

```
c4mp plan add store Main --id main --parent shop.api --tech postgres --repo . --yes --meta reader=drizzle --meta source=src/db/schema
```

A JSON file works the same way: a `store` with `--tech json`, a `record` for the file, and a `field`
inside a `field` for nested data (`address` holding `city`).

**How c4mp reads a store.** c4mp reads the schema code, never a live database. A reader turns the code into records
(tables) and fields (columns). Two readers exist:

| reader | technology | files it reads |
|---|---|---|
| `drizzle` | postgres | `.ts` files that mention `drizzle-orm/` |
| `sql-migrations` | postgres, mysql, sqlite | `.sql` files in a migration folder, named like Flyway files, or holding `CREATE TABLE`; applied in migration order, so an `ALTER TABLE` in a later file changes the table |

The `reader` key picks the reader. Without it, c4mp takes the reader that serves the technology. When two readers
serve it and both find files, the store is ambiguous: set `reader`. `source` limits the reader to one file or folder.
Test files are never read. A plan record matches a code record by its link first (`link <file>#<table>`), else by name
(its title or local id is the table name). A plan field matches a code field by name in the same way.

**Ids of storage elements.** A plan store, record or field has its fqn (`shop.api.main.users`). A record only the code
has is `<file>#<name>` (`db/migrations/0001_init.sql#invoices`). A field only the code has is `<file>#<name>.<field>`
(`db/migrations/0001_init.sql#invoices.user_id`); this is also the id of a code-only field under a plan record
(`db/migrations/0001_init.sql#users.full_name`). A nested field adds `.<child>`. The `unplanned-record` finding and the
storage view use these ids.

**What `check` says about storage** (section 8 has the table). The storage rules run only when the plan has a store.
They compare each store's code with the plan: a store with no code (`missing-store`), a store c4mp cannot read
(`store-unreadable`), a plan record not in the code (`missing-record`), a planned record that is built
(`planned-but-built`), a field that differs (`field-drift`), and code the plan lacks (`unplanned-record`,
`unplanned-store`). The severity follows the status of the element: `planned` info, `in-progress` or no status
warning, `done` critical. Real `check` output, a copy of the fixture `test/fixtures/schema-sql/pg` with this plan
(store `done`, `users` without a status, `classes` and `payments` planned):

```
main = store 'Main' {
  technology 'postgres'
  metadata { status 'done'  owner 'K'  source 'db/migrations' }
  users = record 'users' {
    email = field 'email' { metadata { type 'varchar' } }
    ghost = field 'ghost'
  }
  classes = record 'classes' {
    metadata { status 'planned' }
  }
  payments = record 'payments' {
    metadata { status 'planned' }
  }
}
```

```
info     missing-record  shop.api.main.payments  record 'payments' is not in the code of store shop.api.main (reader sql-migrations)
info     planned-but-built shop.api.main.classes  classes is planned but code exists: db/migrations/0001_init.sql:14; update the status?
warning  field-drift     shop.api.main.users.email  users.email: type 'varchar' in the plan, 'text' in the code
warning  field-drift     shop.api.main.users.ghost  users.ghost: extra in the plan, the code has no such field
warning  field-drift     shop.api.main.users  users.id: missing in the plan (the code has it, type 'uuid')
   ... one line per column of users the plan does not list ...
info     unplanned-record db/migrations/0001_init.sql#invoices  record 'invoices' (line 30) is not under store shop.api.main
info     unplanned-record db/migrations/0001_init.sql#class_members  record 'class_members' (line 22) is not under store shop.api.main
```

`classes` lists no field, so it is checked by name only: its columns give no `field-drift`.

**See the code behind a store or a record.** `c4mp plan show <store>` prints a `code:` line: the reader and the number
of records, or why there is none. `c4mp plan show <record>` prints, for a record the code has, its file and lines, how it
matched (`by link` or `by name`) and one row per code column (type, `pk`, `null`, `fk <table>.<column>`, `on delete`).
Same plan, real output:

```
record  users

fqn:       shop.api.main.users
parent:    shop.api.main
as:        table
code:      db/migrations/0001_init.sql:5-12 (by name)
           id          uuid                      pk
           email       text
           full_name   text                      null

           updated_at  timestamptz               null

```

`c4mp find <name> --kind record` finds tables by name, and `c4mp outline <file>.sql` lists the tables of a migration
file with their columns (`c4mp guide ai`, section 4).

**The storage view.** `c4mp view` adds it to the map page when the plan has a store. Open it with the **Storage**
button of the view switch in the top bar (Architecture view, IO view, Storage view), or add `#storage` to the page
address. The button is disabled when the plan has no store. With the setting "Open a view in: New window" (the
default) the button opens the view in its own window, which shows only the map.

- It draws one dashed zone per container that holds stores, the stores inside it, and one box per record with one row
  per field: a `PK` or `FK` tag, the name, the type, and `?` when the field can be null.
- An arrow goes from each FK row to the row it points to; `cascade` is written on the arrow.
- A record only in the code has a dashed border. A record only in the plan has a grey header. A field with a
  `field-drift` finding has a coloured bar on its left.
- A record or field only in the plan, and a store with no code, are plan-only: the left tree marks them
  `planned (no code yet)`, as on the architecture map.
- With a simulation selected (an s-item, `c4mp guide ai`, "Simulations (s-items)"), the records it names get a ring
  and their step numbers, and once you zoom in far enough their sample rows show under the fields.
- Select a record (on the map, in the tree or from the search) and the records joined to it by an FK light up. The side
  panel shows its file and line, whether it is in the plan, the code or both, its fields, its FKs out and in, its
  indexes and checks, the components that own its file, and its b-items. A field shows its type, PK, null, unique, FK,
  on delete and how it differs from the plan.
- The search finds stores, records and fields by name (Names), and by type, FK, on delete, index, check or description
  (Content).

**IO view kinds** (the IO view). Six kinds describe what a person sees and does in an app: `screen`, `region`, `control`, `state`, `flow`, `journey`.
They need no code link (like `person` and `store`). A plan with no `screen` has no IO view.

```
container     an app (a web app, a phone app)
  screen      one page or view of the app
    region    a part of the screen (a header, a form, a list)
      control   something to press or type into (a button, a link, a field)
        state     a way the thing looks (error, empty, loading)
```

Where each kind may go (`plan add` refuses any other parent):

| kind | parent |
|---|---|
| `screen` | a container |
| `region` | a screen |
| `control` | a screen or a region |
| `state` | a screen, a region or a control |
| `flow`, `journey` | no rule yet: `plan add` cannot create them. They parse, show in `plan show` and `check` accepts them, but the IO view does not read them yet |

In the IO view the words change: a container is an **App** (the top box is **All apps**), a `screen` is a **Screen**.
The IO view has no C1, C2 or C3 level words: the word comes from the kind (`Region`, `Control`, `State`, `Flow`, `Journey`).

**Navigation.** Write a relation. A screen is reached from a screen, or from one of its own parts:

| You write | It means |
|---|---|
| `screen -> screen` | the first screen can open the second |
| `control -> screen` (also from a region or a state) | pressing that control opens the screen; the arrow is drawn between the two screens |

The label is optional. A label you give (`plan relate ... --label "after sign in"`) is shown on the arrow and on the control's row.
Without a label, the arrow has no text; the control's title is not used on the map (the model keeps it as a fallback name).
Several relations between the same two screens draw one arrow; their different labels are joined with `, `.
A screen that points at itself draws nothing. A relation between two parts of one screen is not navigation and is dropped.

**Calls.** A screen, or a part of it, can say which architecture element it uses. Write a relation to a component, or to a planned function, class or type:

| You write | It means |
|---|---|
| `screen -> component` or `control -> component` | the screen calls the component, or the component implements the screen |
| `screen -> function` or `control -> function` (also class, type) | the same, to one function; `toComponent` is the component that holds it |

The label is optional and is kept only when you write it. A call is not a screen arrow: it is listed in the page data (`C4PM_DATA.nav.calls`, with `from` the screen and `via` the control, or `null`).
For a call to a function, use `plan relate` with the function as the target: `c4mp plan relate shop.web.cart.checkout shop.api.carts.addItem --repo . --yes`. A planned function, class, method or type can be the `<from>` or the `<to>` of `plan relate`.

**Metadata of a screen** (quoted values, like all metadata):

| Key | Value | Effect |
|---|---|---|
| `device` | `web` or `phone` | the shape of the screen card: a 4:3 box (`web`) or a tall phone box (`phone`); also the size a wireframe is laid out at |
| `design` | a URL or a repo path, any text | where the design (a picture, a Figma page) lives; kept with the card, not opened and not checked |
| `viewport` | `'<W>x<H>'`, whole numbers 10 to 99999, for example `'1440x900'` | the size the screen's wireframe is laid out at, instead of the device size (`web` 1280 x 800, `phone` 390 x 844). A bad value is `invalid-metadata` (warning) and the device size is used |

Without `device`, c4mp decides. The card is a `phone` when the container's technology, the container's title, the screen's title or the screen's fqn
contains one of `mobile`, `ios`, `android`, `phone`, `flutter`, `react native`, `swift`, `kotlin` (any case, anywhere in the text, so `Scenarios` matches `ios`). Otherwise it is `web`.
A `device` value other than `web` or `phone` is ignored and the rule above decides. Set `device` yourself when a name matches by accident.
Any part (region, control, state) takes `status` like other elements; it shows on the row.

**Check rules for these kinds.** Two things matter:

- `relation-target-missing` (warning): a relation written inside a screen, command, route or tool, or one of their parts, points to an fqn that is no plan element. Fix the target. Real output:
  `warning relation-target-missing shop.web.cart.checkout  shop.web.cart.checkout: relation to 'shop.api.nope' (.c4mp/projects/demo/plan/shop.c4:44) matches no plan element`
- `missing-code` is not asked of these kinds (a `done` screen needs no link). A planned function you point at gets the usual info `planned-not-built`.

A relation from a screen to a region, control or state of another screen is accepted by `check` but not drawn.

**Wireframes: where each part of a screen sits.** The plan says which regions and controls a screen has. A wireframe
says where each one sits and how big it is. It is plain HTML, one file per screen. The browser lays it out, and the
IO view draws the boxes in c4mp's own style. A screen without a wireframe is drawn as stacked strips.

- **File.** The wireframe of screen `S` is `<plan folder>/io/<fqn of S>.html`, for example `io/shop.web.home.html`.
  The plan folder is the folder that holds the `.c4` files (section 1, order 1 to 3). A plan read from the whole
  repo (order 4) has no plan folder, so it has no wireframes. The plan reads only `.c4` files, so `io/` changes
  nothing in the plan. Put no `.c4` file in `io/`: it would be read as part of the plan.
- **Fragment.** The file is an HTML fragment: no `<html>`, `<head>` or `<body>`.
- **Nest it like the real UI.** Write the elements the way the real page is built: a page, a top bar, a main row,
  side panels. Nesting only gives the position. The plan says who owns what, so a control may sit in another
  element in the HTML than in the plan.
- **`data-c4`** links an element to a region or control of this screen. Write the part's id (`search`). When that id
  is used twice under the screen, write the dotted path from the screen (`top_bar.search`); a dotted path always works.
  Only parts of this screen count, and titles are never used. A ref that names two parts is its own problem
  (ambiguous), not a missing part. The same ref may sit on two elements: one part drawn in two places.
- **Elements without `data-c4`** only shape the layout (wrappers, spacers). They are not drawn.
- **States** are not placed: they show in the panel. A `data-c4` that names a state is allowed, never required.
- **`hidden`** marks a part that is shown only sometimes: a popup, a drawer. It is laid out as if shown and drawn
  dashed, with everything inside it.
- **Classes only.** A wireframe carries only classes. Every size and position lives in one global stylesheet,
  `io/site.css`, and every screen links it with `<link rel="stylesheet" href="site.css">`. Change a class there and
  every screen that uses it follows. `style` attributes and `<style>` blocks still lay out, but `check` reports them
  (`wireframe-inline-style`). A `<link>` must be `rel="stylesheet"` with a relative `.css` path that stays inside
  `io/` (no `..`, no leading `/`, no URL); any other link is dropped (`wireframe-bad-stylesheet`). The build puts
  the sheet into the page, so the viewer fetches nothing.
- **Layout properties only.** These CSS properties are kept; a name that ends in `*` is a prefix (`grid*` keeps
  `grid-area`, `inset*` keeps `inset-inline`):

<!-- wireframe:css -->
`display`, `flex*`, `align-*`, `justify-*`, `place-*`, `order`, `gap`, `row-gap`, `column-gap`, `grid*`, `width`, `height`, `min-*`, `max-*`, `padding*`, `margin*`, `position`, `top`, `right`, `bottom`, `left`, `inset*`, `box-sizing`, `aspect-ratio`, `z-index`
<!-- /wireframe:css -->

  Everything else is removed before layout: colour, background, font, border, transform, animation, `--custom`
  properties. Colours never go in a wireframe file: c4mp draws with its own theme colours. `calc()` values are fine.
  Only plain style rules are kept; `@import`, `@media`, `@font-face` and nested rules are dropped.
- **What else is removed.** Only structural and form tags are kept (`div`, `section`, `nav`, `button`, `input`,
  `select`, ...). Any other tag (`script`, `img`, `svg`, `iframe`, ...) is removed with its content. `form` becomes a
  `div`. Only the attributes `class`, `id`, `style`, `data-c4` and `hidden` are kept. Text is kept for sizing but
  never drawn: c4mp draws the plan titles.
- **Base style.** Before the file's own classes, c4mp applies `box-sizing: border-box`, no margin, padding or
  border, `appearance: none` and a fixed 12px font, so a file lays out the same in every browser and theme.
- **Explicit sizes.** Fonts and form controls still differ between systems. Give everything that holds text, and
  every form control, a width and a height (a class in `io/site.css`).
- **Viewport.** The layout runs at the device size: `web` 1280 x 800, `phone` 390 x 844 (the device comes from
  `device` or the rule above). `viewport '<W>x<H>'` on the screen sets another size. The root element fills the
  viewport (`height: 100%` works). The frame on the map has the same aspect, and its title row shows the size.

Example: screen `home` of `shop.web` has the region `top_bar` (controls `logo`, `search`, `cart_btn`), the regions
`filters` and `footer`, and the region `products` (control `sort`). Its wireframe `io/shop.web.home.html`:

```html
<link rel="stylesheet" href="site.css">
<div class="page">
  <div data-c4="top_bar" class="row topbar">
    <button data-c4="logo" class="btn btn-m"></button>
    <div class="grow"></div>
    <button data-c4="search" class="btn field"></button>
    <div class="grow"></div>
    <button data-c4="cart_btn" class="btn btn-s"></button>
  </div>
  <div class="main">
    <div data-c4="filters" class="sidebar"></div>
    <div data-c4="products" class="grow anchor">
      <button data-c4="sort" class="btn btn-l corner"></button>
    </div>
  </div>
  <div data-c4="footer" class="footer"></div>
</div>
```

and the one global `io/site.css`, shared by every screen:

```css
.page    { display: flex; flex-direction: column; height: 100%; }
.row     { display: flex; align-items: center; }
.main    { display: flex; flex: 1; }

**CLI, API and MCP**. A command line tool, an HTTP API and an MCP server are drawn like screens. Eight more kinds:

```
container     an app (technology says CLI, API or MCP)
  command     a command; a subcommand is a command under a command
    options   a group of options (optional)
      flag      --json, --file <path>
    flag      a flag without a group
    arg       <name>
  route       an API route, titled like "GET /orders/:id"
    param     a path or query parameter (metadata in, type, required)
    body      the request body
      param     a field of the body
  tool        an MCP tool
    param     an input of the tool
```

Where each kind may go (`plan add` refuses any other parent):

| kind | parent | shown as |
|---|---|---|
| `command` | a container, or a command (subcommand) | Command |
| `options` | a command | Option group |
| `flag` | a command or an options group | Flag |
| `arg` | a command | Argument |
| `route` | a container | Route |
| `body` | a route | Body |
| `param` | a route, a body or a tool | Param (Field under a body) |
| `tool` | a container | Tool |

`command`, `route` and `tool` are the cards of the IO view (like `screen`); the others are rows on the card. Each subcommand is its own card, titled with its full path (`plan show`).
Unlike a screen, a `command`, `route` or `tool` that is `done` or `in-progress` needs a `link` to its code (check rule `missing-code`); its parts need none.
The word of an app comes from its `technology`: commander, yargs, click, cli give **CLI**; express, fastify, hono, rest, http, api, openapi give **API**; mcp gives **MCP**; anything else stays **App**.
The title is shown as written (`--json`, `<target>`, `GET /orders/:id`). A route takes its HTTP method from `--meta method=GET`, else from the first word of the title when that is GET, POST, PUT, PATCH, DELETE, HEAD or OPTIONS.
A `param` takes `--meta in=path|query|header|body` (default `query` under a route, `body` under a body), `--meta type=<text>` and `--meta required=true`; they are kept as written and not checked.
A relation from a command, route or tool, or from one of its parts, to a component or planned function is a call, like a screen's (`plan relate <command> <component>`). Readers that fill these kinds from code come later; for now you write them.

## 4. Syntax reference

```
// line comment            /* block comment */        (NOT '#')

specification { ... }      skipped by the parser (kept for editors)
views { ... }              skipped
model {
  <id> = <kind> '<title>' ['<description>'] {   // body is optional
    technology '<text>'
    description '<text>'
    title '<text>'                // replaces the title
    link <path>[#<function>] ['<link title>']
    metadata {
      <key> '<value>'
    }
    <childId> = <kind> '<title>' { ... }          // nested element
    -> <target-fqn> ['<label>']                   // relation from this element
  }
  extend <fqn> { <elements and relations> }       // add children to an existing element
  <from-fqn> -> <to-fqn> ['<label>']              // relation
}
```

Rules, all verified in `lexer.ts` / `parser.ts`:

- Strings use single OR double quotes; escape the quote char or backslash with `\`. A string may span
  lines. An unclosed string gives `parse-error ... unterminated string`.
- Links may be bare (`link ../x.ts`), or quoted. A bare link ends at whitespace or a brace.
- Relations: `<from> -> <to> ['<label>']`. Write FULL fqns on both sides: the parser stores the ids
  exactly as written (no prefixing, even inside `extend`). A relation to an id that is not an
  element is stored without error.
- **Every metadata value MUST be quoted.** An unquoted value (`status done`) is a parse error on that
  line: the value is not stored, the other keys of the block are kept. Real run, a component with
  `status done` and `owner 'K'`: `plan show` ends with
  `.c4mp/projects/notes/plan/a.c4:16 metadata value must be quoted (key status)`, `check` reports
  `warning  parse-error     .c4mp/projects/notes/plan/a.c4  .c4mp/projects/notes/plan/a.c4:16 metadata value must be quoted (key status)`,
  and `plan show <fqn>` shows `owner:     K` and no status.
- A metadata line whose key is not a plain id is skipped without error.
- A lone word on its own line (no `=` or `->`) gives `parse-error ... stray word '<id>': expected = or -> after it`;
  the next line is still read as written.
- Anything else the parser does not understand gives a `parse-error` finding, e.g. a `#` comment
  line inside an element: `parse-error ... plan/broken.c4:3 unexpected word`.

Metadata keys that c4mp reads on elements of any kind (screens, storage and IO kinds have more keys, listed in
their sections; other keys are parsed and kept, but nothing uses them):

| Key | Used for | Allowed values |
|---|---|---|
| `status` | map pill, `check` rules | `planned`, `in-progress`, `done`, `abandoned` |
| `owner` | map pill; `done` without owner warns | any text |
| `sprint` | map pill; `late` rule | `S` + number: `S15` |
| `priority` | map pill | `high`, `medium`, `low` |
| `tags` | search; no map pill | comma separated words of lower-case letters, digits and dashes: `billing, api-v2` |
| `layout` | box positions on the map | machine written, see section 6 |
| `shared` | a subregion only: drawn as a column beside the other subregions (section 2) | `true` |
| `uid` | the element's stable identity (board links, `plan show <uid>`); written by `c4mp plan ids` and the plan commands; never edit it (`plan set` refuses it). `check`: `duplicate-uid`, and `invalid-metadata` "uid '<v>' is not a UUID" | a UUID, machine written |
| `signature` | planned functions and methods (section 13); `missing-signature` when a `planned` one has none | the code signature: `'addItem(cartId: string, sku: string): Cart'` |
| `purpose` | planned functions, classes and types (section 13) | any text |

`check` warns (`invalid-metadata`) for each tag that breaks the format, e.g. `Billing`; a missing
`tags` key is never a finding. The search box matches a box by its tags.

Other keys (for example `team`) survive a re-run of `plan generate` but do nothing. The four keys
`status owner sprint priority` are written first, then the remaining keys sorted, whenever
`plan generate` builds a new block (a block you already have is copied as written). `technology` is a body line, not metadata; on a container it is the
subtitle shown on the map, verbatim.

## 5. Claims: how a component points at code

A `link` inside a component is a claim: "this component owns that code".

| Link | Kind | Covers |
|---|---|---|
| `link ../../../../api/src/models/` (ends with `/`) | folder | every function in every scanned file under that folder |
| `link ../../../../api/src/server.ts` | file | every function in that file |
| `link ../../../../api/src/services/orderService.ts#OrderService.create` | function | exactly that function or method |
| `link ...#L10-L20` | lines | the WHOLE file, like a file link (the range is ignored for ownership); `check` reports `line-link` (info). Avoid. |
| `link https://...` | URL | kept as written, claims nothing |

Function names are exactly the names in the scan outline: `create` is a method of a class and is
named `OrderService.create`; top-level functions use their plain name (`makeOrder`, `orderRoutes`).
Check names with `c4mp plan resolve-link <path>#<name> --repo <repo>` before writing them.

Link paths are relative to the folder of the `.c4` FILE that contains them, not to the repo root:

From `.c4mp/projects/<id>/plan/x.c4`, `..` is `projects/<id>`, `../..` is `projects`, `../../..` is
`.c4mp`, `../../../..` is the anchor (usually the repo root). So write
`link ../../../../<path from the anchor>`; if the scanned code folder is below the anchor, include
its subfolder. Copy an existing `link` line and change the tail. A wrong `..` count shows in
`check` as a path starting with `.c4mp/`: with three `..` the real run printed
`Pay is done but its code is missing: .c4mp/web/src/components/Cart.jsx`.

### Claim mode versus folder mode

A plan is in claim mode when at least one component link has a `#function` name (and no line range).
Otherwise it is in folder mode. This switch changes what the map and `check` do:

| | folder mode (no `#function` link anywhere) | claim mode (at least one `#function` link) |
|---|---|---|
| Map shows | the SCANNED containers/components (from folders); the plan only supplies status/problems | the plan's containers and components (plus the scanned containers) |
| Plan-only components with no code | NOT on the map | on the map (see section 10) |
| `check` ownership rules | `unplanned-code` | `component-claim-conflict`, `split-file`, `shared-auto`, `unassigned-code`, `test-only-code` |

### Who owns a function (claim mode)

Per function, every claim that matches competes:

1. Most specific wins: function (rank 3) beats file (2) beats folder (1). A component holding
   several matching claims counts with its best one.
2. Tie between DIFFERENT components of the same rank: the component that comes first in plan order
   wins. Plan order is the element ids sorted alphabetically (`localeCompare` on the fqn), NOT the
   order of files or lines. (Real run: `sample_shop.api.models` beat `sample_shop.api.order_handling`
   for `makeOrder`, both held the folder `api/src/models/`.) The loser gets a
   `component-claim-conflict` warning with reason `plan-order`, or `specificity`.
3. No claim matches: the function is `shared` if some file owned by a component imports its file
   (a file-level approximation, there is no call graph), otherwise `unassigned`.
4. Test files (config `tests.globs`, role `test`) neither give nor take ownership: a test file never
   makes its component a user, and code that only test files reach is `test-only-code` (info), not
   `unassigned-code`. Test files get no `unplanned-code`, `unassigned-code` or `split-file`.

There is no `.c4` syntax to declare shared code. To make shared code permanent, claim it with a
component (for example `shared_utils = component 'Shared utilities'` with `link .../lib/`); then it
is owned and `shared-auto` disappears. UNVERIFIED on a real run: the shared-auto output line (only
read from the code).

## 6. Layout metadata (do not hand-edit)

```
layout '19271,25827;4977,13349,33178,23922'      // bx,by ; rx,ry,rw,rh
layout ';44790,13349,38178,26922'                // no bubble position
```

Both lines are real values from a plan (each inside an element's `metadata { }`). Format
(`parseSavedLayout`): optional `bx,by` (the small closed shape), `;`, then `rx,ry,rw,rh` (the region
the node opens into); integers, `rw` and `rh` above 0, in map world units relative to the PARENT
region's top-left (the root is absolute). A non-matching value is ignored without error. It is
written by `c4mp plan apply-layout --file c4mp-layout.json` (or by Save layout in a page served by `c4mp serve`) from a layout the human exports in the
viewer. An entry `null` in that file removes the element's saved layout: the viewer writes it for a box
or subregion the plan placed that is back at its automatic place (the **Auto arrange** button in edit mode
puts the selected container or subregion back to the automatic layout). A subregion is
saved like a c-item once it is placed (moved or resized in edit mode): `rx,ry` is the slot centred on its
frame and `rw,rh` the frame size, both in its container's units, with no `bx,by`; a subregion never
placed has no `layout` and its frame follows its components. Do not hand-edit or delete `layout` lines: the numbers only mean something to the viewer
and the human placed those boxes.

The `sim-*` rules read the s-items (simulations: flows and journeys, one file each in `.c4mp/projects/<id>/sim/`).
They run in `check`, `status`, MCP `check` and `view`, only when the project has a `sim/` folder: no s-items, no
finding. The `person` of an s-item is free text and never a finding.

A `planned` component whose link points to nothing yet produces no finding (shown in section 10).

The `wireframe-*` rules read the plan and the files in `io/` (section 2, "Wireframes"). They run in `check`, `status`,
the MCP `check` tool and `view`, never in the safe-edit gate (section 14), so a plan edit is never refused because
of a wireframe.

The storage rules (`missing-store` to `unplanned-store`, and `planned-but-built` for a record) read the plan and the
store code (section 2, "How c4mp reads a store"). They run in the same places, also never in the safe-edit gate.
- They run only when the plan has a `store`. A plan with no store gets no storage finding, not even
  `unplanned-store`, so `check` stays fast on a repo without a storage plan.
- "By status" means the status of the element the finding is about: `planned` info, `in-progress` or no status
  warning, `done` critical. A `field-drift` on a field with no status takes its record's status. An `abandoned`
  store, record or field gets no finding, and neither does what is under it.
- `missing-store` is a store with no code files: no reader serves its technology, or the reader finds no files. Its
  records then get no `missing-record`. `store-unreadable` is only a real read failure: an ambiguous technology, an
  unknown reader id, a live reader, a reader limit, or a reader error.
- A plan record that lists no field is checked by name only. Once it lists one field, every code column it does not
  list is a `field-drift` "missing in the plan".
- `unplanned-record` and `unplanned-store` are always info. `c4mp plan unplanned --view storage` lists exactly these
  two rules of the same findings.

## 9. Edit checklist for agents

1. Read first: `c4mp plan show --repo R` (structure and statuses), `c4mp status --repo R`, and the `.c4` files.
2. Edit only inside the plan folder. Never edit `.c4mp/projects/*/data` or `history`, or `C4MP/`
   (regenerated). Never edit source code to satisfy the plan.
3. Keep ids stable. An id is an identity: renaming `a.b.c` by hand breaks every relation, `extend` and
   `layout` that mentions it, and the saved box positions. When an id or a parent must change, use
   `plan rename` or `plan move` (rule 8).
4. Quote every string, including every metadata value. Use `//` comments.
5. `plan generate` rewrites `architecture.c4` and every `<container>.c4`, but it copies the block of every
   element the plan already has as you wrote it: comments, `description`, `technology`, `link`s,
   `metadata` and any other line inside the braces survive a re-run. It only adds elements the plan
   does not have (new scanned components in `<container>.c4`, new containers inside the system block).
   Comments above a block (outside the braces) are not kept. Hand-written elements that no file
   generate rewrites holds (for example `orders.c4`) are not touched at all.
6. Test paths and names first: `c4mp plan resolve-link <path>#<name> --repo R`.
7. Run `c4mp check --repo R` (same `--lang` as before) after EVERY `.c4` edit and report what remains.
8. Never delete an element block by hand without checking its children and the relations that name it
   (`grep` the fqn in all `.c4` files). Prefer `c4mp plan remove <target> --repo R` (dry run by default;
   `--yes` writes; `--relations` also removes the plain relation lines that name it). To move or rename an
   element, use `c4mp plan move <element> --parent <target> --repo R` or `c4mp plan rename <element> <new-id>
   --repo R`, never `sed` or cut and paste: they rewrite every relation end and `extend` that names it, in all
   files, rename its wireframe files, and list the mentions in comments, strings, docs and the board.
9. Do not edit `layout` lines (section 6).
10. To add, change, link, relate, move or rename an element, prefer the commands `plan add`, `plan set`, `plan link`,
    `plan relate`, `plan move`, `plan rename` (section 14): they quote values for you and refuse an edit that makes
    the plan worse.

## 11. Common mistakes

| Symptom | Cause | Fix |
|---|---|---|
| `parse-error ... metadata value must be quoted (key status)` | Unquoted metadata value (`status done`) | `status 'done'` |
| `parse-error ... unexpected word` | `#` comment, or stray text in a body | Use `//` |
| `missing-code ... .c4mp/web/...` | Wrong number of `..` in `link` | Four `..` from `.c4mp/projects/<id>/plan/` (plus any subfolder of the anchor) |
| `broken-function` | Wrong function name | Use `plan resolve-link`; methods are `Class.method` |
| Planned components/containers do not show on the map | Folder mode (no `#function` link in the whole plan) | Add one `#function` link (section 10) |
| Two boxes with the same title (for example "Root") | Plan container id differs from the scanned id | Rename the plan container to the scanned id (`_root`, `app`, ...) |
| My title, new component or relation vanished after `plan generate` | Generated files are rewritten | Put hand-written parts in separate `.c4` files |
| `component-claim-conflict` after adding a component | Your links overlap another component | Narrow the old component's links, or accept the winner |
| `unassigned-code` for a function | No component claims its file and nothing imports it | Add a claim, or move it under a component |
| `plan generate` wrote to a different project folder than `init` | `init` uses the folder name, others use `package.json` name | Use the folder that holds the `.c4` files |
| An element, and its relations, missing on the map; no error | Unknown kind word (`w = widget 'W'`: `plan show` lists `[widget]`, the map has no box and drops `notes.app -> w`) | Use a kind of section 2; `person` / `external` for users and outside systems |
| `parse-error ... unterminated string` | Missing closing quote | Close it |

         test-only-component

```

## 13. Planning functions, classes and types

A `function`, `class`, `method` or `type` element nested under a component plans code that may not exist yet. The kinds are listed in `PLANNED_CODE_KINDS` in `Project/src/plan/plannedElements.ts`. The commands in this section were run on a copy of the level-4 fixture (`Project/test/fixtures/level4`) in `/tmp/c4mp-p14/l4-8`, from `Project/` with `npm run cli -- <command>`. `R` below is that repo root.

### Syntax

Shape taken from the fixture plan `c4/plan.c4`:

```
billing = component 'Billing' {
  link ../src/built.ts#buildInvoice 'Invoice builder'

  plan_fn = function 'planFn' {
    link ../src/planned.ts#planFn
    metadata {
      status 'planned'
      signature 'planFn(): void'
    }
  }
}
```

### Metadata keys and title

- The title is the code name (`planFn`). `PlannedCode.name` is `element.title` (`extractPlannedCode` in `plannedElements.ts`).
- `status`: read by `checkPlan` in `check.ts`. Values in the check output: `planned`, `in-progress`, `done`.
- `signature`: read by `extractPlannedCode` in `plannedElements.ts`. `missing-signature` fires when a function or method with status `planned` has none (`checkPlan` in `check.ts`).
- `purpose`: read by `extractPlannedCode` in `plannedElements.ts`. No output in this section uses it (not verified).
- `owner`: required when `done` (`validateMetadata` in `validate.ts`; output `invalid-metadata`).

### Links

- Format: `link <path>#<name>`. The `<path>` is relative to the `.c4` file (`../src/planned.ts` from `c4/plan.c4`).
- The element's code link is the first link that has a name (`plannedElements.ts`, `extractPlannedCode`).
- `resolve-link` takes a path relative to the repo root, not to the `.c4` file: `c4mp plan resolve-link src/stub.ts#stubbed --repo R`.

### A nested link claims nothing

- `extractClaims` in `Project/src/c4/ownership.ts` reads `links` only of elements whose kind is `component`. A `#name` link on a nested function does not claim code.
- `isClaimModePlan` in `ownership.ts` uses the same extraction, so claim mode needs a component-level `#name` link.
- In the fixture, `billing` has one (`built.ts#buildInvoice`), so the plan is in claim mode. `reports` has none, so its nested `stub_fn` claims nothing, and `src/stub.ts#stubbed` is reported as `unassigned-code` (critical).

### Workflow

1. Under the component, add a `function` (or `class`, `method`, `type`) element with the code name as title, `status`, `signature`, and `link <path>#<name>`.
2. `c4mp plan resolve-link <path>#<name> --repo R`: `found: true` means the function exists. The result gives its line range.
3. `c4mp check --repo R`: `planned-not-built` shows until the code exists. After that, `planned-built-update-status` shows while the status is still `planned`.
4. `c4mp stubs --repo R`: lists functions that only throw. Set `done` after the stub is implemented. (Whether `stub-in-done` covers a nested element: not verified.)

### Tests attached to c-items (Phase 26)

Tests are not part of the plan's structure: no test component, no test container, no test box on the map (a plan
component whose files are all tests gets `test-only-component`). At every scan c4mp finds the test cases in the test
files (config `tests.globs`) and hangs each on the lowest c-item its body exercises: one function or method gives that
function; several functions of one component give the component; several components give their container (subregions are
skipped); several containers give the system. Where you see them:

- On the map: a test count pill on each box (the Tests toggle of the legend hides it), and a Tests section in the right
  panel: tests to run (with the run command and a Copy button), tests to write, and tests attached elsewhere that touch
  the box.
- From the command line: `c4mp plan show <c-item>`, `c4mp show <file#function>`, `c4mp board show <id> --with-tests`;
  MCP `plan_show`.

The plan stores only what a scan cannot know: tests still to write and hand links, as `test` blocks (next part). Real
outputs, run commands per language, config keys and limits: `c4mp guide ai`, "Tests attached to c-items".

### Test blocks: tests to write and hand links (Phase 26, plan standard 1.5)

A test is an accessory of the element it tests, not an element: no uid, no box, no tree node, no board link. It is a
`test` block in the body of a `container`, `component`, `function` or `method`:

```
billing = component 'Billing' {
  link ../src/billing.ts#charge
  test 'refunds a partial charge' {}
  test 'cli help' { case 'test/cli-help.test.ts#help › lists commands' }
  test 'every case of the helper' { case 'test/helpers/runCli.ts' }
}
```

- Without `case`: a test to write. `check` reports `planned-not-built` (info, id = the parent, message
  `test '<name>' not written`) until a detected test case matches the name: the full chain (`describe › it`) equal, or the
  leaf (text after the last ` › `) equal and unique among every test case of the repo.
- With `case`: a hand link. The value is a test case id (`file#describe › name`) or a test helper file (it then covers
  every case that uses it). It is never a `link` line (a `link` claims code). A case id link puts that case on the
  block's parent, whatever its calls reach (the place found from the code stays in its touches). A helper file link adds
  the parent to what every case using the helper reaches (for a helper that spawns a built CLI, say). `check` reports
  `test-link-dead` (warning) when the value names no test case and no test file any more.
- Found without a link: a string in a test that is exactly a scanned file path, from the repo root or from the test's
  folder (`'viewer/panel.js'`, `'../viewer/panel.js'`), counts as using that file when it goes into a file, path or
  process call (`fs.*`, `path.join`, `spawn`, ...) or into a test helper that passes it to one; a string in a data table
  or an `expect` does not. Build output (`dist/bin/cli.js`) is not scanned and is never mapped back to its source: link
  those tests by hand.
- One line per block: tools write `test 'n' {}` on one line, because a reader before 1.5 skips only the rest of the line
  after a word it does not know (a block over several lines would close its parent early there). `c4mp` reads both.
- `c4mp plan add test "<name>" --parent <target> [--case <test id | helper file>] --repo R [--yes]` writes the line at the
  end of the parent's body (dry run without `--yes`). Refused: a parent of another kind, a second block with the same
  name, a `--case` that is neither a scanned test case id nor a test file, any element option (`--status`, `--link`, ...).
- `c4mp plan remove <target> --test "<name>" --repo R [--yes]` removes one block through the write gate.
- The write gate refuses any edit that loses a test block (only `plan remove --test` may; `plan move` and `plan rename`
  take the blocks along). `plan generate` writes the blocks back as they were.
- `no-tests` (info) is off by default. Turn it on with config `"tests": { "noTests": true }`: `c4mp check` (CLI and MCP)
  then reports each plan component on the map with no test attached to it or below it and no test block on it or below it.

## 14. Editing a plan with commands

Six commands edit the plan for you: `plan add` (container, component, planned code), `plan set` (fields of one
element), `plan link` (code link), `plan relate` (relation), `plan move` (elements to a new parent) and
`plan rename` (a new id). The full option list is in the AI guide, section 4 (`c4mp guide ai`). How they change
the file:

- **Dry run first.** Without `--yes` they print the diff and write nothing. A dry run that would be
  refused exits 1.
- **Only the intended lines change.** Every other byte stays, including `layout` and existing `uid`
  lines (`plan move` carries them with the block). A new system, container, subregion or component gets a `uid`; planned code gets none.
- **Values are quoted for you** (`\'` and `\\` escapes, section 4). Because an unquoted metadata value is
  a parse error and is not stored (section 4), prefer `plan set` to typing metadata by hand.
  `plan set` checks `status`, `priority` and `sprint` (`S15`) and refuses `uid` and `layout`.
  `plan set <x> title=...` changes the title only; the id (and so every relation and `layout` line that names
  it) stays.
- **Where it writes.** A new element goes next to its siblings of the same view (architecture, IO or storage):
  1. into the parent's body in the file that defines the parent, when that file holds such a sibling;
  2. else at the end of the first `extend <parent>` block, in file path order, that holds one;
  3. else into the parent's body in the defining file.
  So a new screen lands in the file with the other screens of its container, and a new component in the file with
  the other components, whatever the file names. `plan generate --view storage` picks the file of a new store the
  same way. A top-level element goes into the `model` block of the file that holds the first system.
  A plan file outside `.c4mp/` and `C4MP/` is refused unless you pass `--force`.
- **Move and rename.** `plan move <element>... --parent <target>` cuts each whole block (with its children,
  `uid` and `layout` lines) and puts it at the end of the new parent's body; `plan rename <element> <new-id>`
  changes the id token only. Both rewrite every relation end and every `extend` target that names the element
  or anything inside it, in all `.c4` files, and rename the wireframe `io/<fqn>.html` of a moved screen. Text in
  comments and strings is never rewritten: it is listed, with mentions in docs and the board, as `file:line  fqn`.
  Comment lines above a moved block stay where they were. All or nothing: every problem is listed and nothing
  is written.
- **The whole plan is checked first.** The edit is refused when it adds a parse issue or a new warning
  or critical finding (old findings never block). Example (real run, `status=in-progress` on a component
  with no link):

```
error: new-findings: the edit would make the plan worse, nothing written:
  - new critical missing-code phofast.api.Loyalty: Loyalty is in-progress but its code is missing: no link
```

- **The folder to claim mode trap.** The first `plan link <component> path#function` switches the whole plan
  to claim mode (section 5); every other function then needs a component, so the edit is refused. Real run:

```
error: new-findings: the edit would make the plan worse, nothing written:
  - new critical unassigned-code src/web/admin/Dashboard.tsx#AdminDashboard: no component claims src/web/admin/Dashboard.tsx#AdminDashboard and nothing calls it
NEXT STEP: link the file or folder without #name to stay in folder mode, or claim every function of it (see: c4mp plan unplanned)
note: this function link switches the whole plan to claim mode (c4.md section 5)
```

## 15. Hooks: history on every commit and merge

`c4mp install-hooks --repo .` adds two git hooks, post-commit and post-merge. Each one starts `c4mp hook <kind>`
in the background (its output goes to /dev/null), so a hook never blocks git and never makes a git command fail.
A run records history, then (if `viewOnCommit` is true, the default) rewrites `c4mpView.html`. The hooks record
the final state only; `c4mp history --repo . --max N` records the full timeline (the N newest first-parent
commits; commits already stored are skipped).

| Hook | Fires after | Records | Drift |
|---|---|---|---|
| post-commit | `git commit` | the new commit (HEAD) | none |
| post-merge | `git merge`, a `git pull` that merges or fast-forwards | the merge result (HEAD), plus the state before the merge (git's ORIG_HEAD) when it is not stored yet | before vs after |

- **Drift** is the state before the merge (ORIG_HEAD) against the state after it (HEAD), both found by commit,
  warning and critical changes only, written to `last-drift.txt` in the project data folder
  `.c4mp/projects/<id>/data/` (git-ignored). A merge or fast-forward of 5 commits adds one history entry (the new
  tip), not 5, and one drift from before to after. No ORIG_HEAD: no drift (`drift skipped: no ORIG_HEAD`);
  ORIG_HEAD equal to HEAD: no drift (`drift skipped: nothing changed`). The drift file is not printed: git
  discards hook output. Compare any two stored commits yourself with `c4mp diff --from <sha> --to <sha>`.
- **One hook at a time** per project. A hook that starts while another one runs waits for it, up to 10 minutes,
  then gives up and logs `skipped: busy` (git is not blocked; the next hook or `c4mp history` catches up). The
  lock is `hook.lock` in the data folder; a lock whose process is gone, or that is older than 6 hours (a hook that
  hangs), is taken over; a live hook that runs long keeps its lock.
- **Its own commit.** The hook script reads HEAD (post-merge: also ORIG_HEAD) with `git rev-parse` before it
  starts c4mp in the background, and passes the shas to `c4mp hook`. Node can take seconds to start, and the next
  git command may have moved HEAD by then; with the shas passed, each of 3 quick commits (or merges) records its
  own commit, and a hook that waits for the one before it still records the state git had when it fired.
  Hooks installed before 0.8.0 read HEAD and ORIG_HEAD only once node runs; they still work, but run
  `c4mp install-hooks --repo <repo>` again to get the new hook script (it replaces the c4mp block only).
- **Finish order.** Waiting hooks poll for the lock, so they are not served in the order git fired them: queued
  hooks may finish in any order (5 quick merges finished as merges 1, 2, 4, 5, 3). Each run still records its own
  commit (its `head` and `refs`) and its own drift (that merge's ORIG_HEAD against its HEAD, the `drift` field of
  its line). `last-drift.txt` holds the drift of the run that finished last; for another merge use `c4mp diff`.
- **`last-hook.txt`**, next to `last-drift.txt` in `.c4mp/projects/<id>/data/`: every hook run appends one line
  when it finishes, so the lines are in finish order, not in the order git fired the hooks, and the last line is
  not always the newest merge. To find a merge's line, match the `head <sha7>` in each line, not the line's
  position. The file keeps the last 20 lines. A hook that finds no `.git` or `.c4mp` anchor writes nothing.
  Real lines (a 3-commit repo: post-commit at the first commit, a `--no-ff` merge of the other two, then the same
  merge with an empty store):

```
2026-11-08T07:26:41.940Z | post-commit | head 0c8725b | refs 0c8725b | drift skipped: not a merge | page written | 15.3 s | maxRSS 88 MB | ok
2026-11-08T07:27:26.288Z | post-merge | head fc62717 | refs fc62717 | drift 0 changes | page written | 55.7 s | maxRSS 76 MB | ok
2026-11-08T07:28:26.179Z | post-merge | head fc62717 | refs 0c8725b fc62717 | drift 0 changes | page written | 31.3 s | maxRSS 96 MB | ok
```

| # | Field | Values |
|---|---|---|
| 1 | start | when the hook started (ISO, UTC) |
| 2 | kind | `post-commit` or `post-merge` |
| 3 | `head <sha7>` | HEAD when the hook fired; `-` when it could not be read |
| 4 | `refs <sha7> ...` | the commits this run added to the history, the before-state first; `none` when all were stored already; `-` when the run did not get that far |
| 5 | `drift ...` | `<N> changes` (details in `last-drift.txt`); `skipped: not a merge` (post-commit); `skipped: no ORIG_HEAD`; `skipped: nothing changed`; `error: <message>` (the history is still recorded); `-` |
| 6 | `page ...` | `written`; `off` (`viewOnCommit` is false); `-` |
| 7 | `<s> s` | seconds the run took, the wait for the lock included |
| 8 | `maxRSS <n> MB` | peak resident memory of the hook process (`resourceUsage().maxRSS`); on macOS it leaves out compressed and swapped pages, so Activity Monitor can show more |
| 9 | result | `ok`; `skipped: busy` (waited 10 minutes for the hook before it); `failed: <message>` (for example a corrupt history manifest) |

- **Batch merges.** Merging many branches in a row fires one post-merge per merge, and they queue. Turn the
  hooks off for the batch and record once at the end:

```
git -c core.hooksPath=/dev/null merge <branch>
git -c core.hooksPath=/dev/null merge <other-branch>
c4mp history --repo . --max 5
```

  `c4mp history` writes no drift file and does not rewrite the page: compare with `c4mp diff`, refresh the page
  with `c4mp view --repo .`.
- **`git pull --rebase`** with local commits replays them on top of the fetched ones: there is no merge, so no
  post-merge fires and no merge drift is written. Run `c4mp history --repo .` to record the new commits.
- A merge that stops on conflicts fires no post-merge either: the `git commit` that ends it fires post-commit,
  which records the merge commit but writes no drift.
